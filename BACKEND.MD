## Технический план backend для "Мини-облако"

### 1. Общая архитектура

- **Стек:**
  - Backend: Spring Boot 3 (Java 21)
  - Безопасность: Spring Security + JWT
  - БД: SQLite (через Spring Data JPA / Hibernate)
  - Хранение файлов: файловая система, структура `backend/cloud/{user_uuid}/{path_inside_cloud}/file`
  - Документация API: OpenAPI/Swagger UI
  - Контейнеризация: Docker + docker-compose
- **Принципы:**
  - Модульность: чёткие слои (controller → service → repository → storage/infra)
  - Без жёсткого хардкода: конфигурация через `application.yml`/env-переменные
  - Лёгкая смена БД/хранилища (SQLite → другая БД / локальный диск → S3 и т.п.) через интерфейсы
  - Явное использование multithreading (асинхронные задачи, предварительная обработка/превью)

Структура пакетов (пример):
- `com.example.acs.config` — конфигурация (security, swagger, storage, async)
- `com.example.acs.user` — сущности пользователя, репозитории, сервисы
- `com.example.acs.file` — файлы, папки, загрузка/скачивание
- `com.example.acs.share` — механизм "поделиться"
- `com.example.acs.quota` — квоты/лимиты
- `com.example.acs.admin` — админские сервисы и API
- `com.example.acs.audit` — аудит/логирование действий (на будущее)

### 2. Модель данных и БД (SQLite)

#### 2.1. Сущности

- **User**
  - `id` (UUID, PK)
  - `username` (уникальный логин)
  - `passwordHash` (bcrypt)
  - `role` (например, `USER` / `ADMIN` — хотя админка имеет свою авторизацию, роль `ADMIN` может пригодиться)
  - `assignedSpaceBytes` (лимит хранилища для пользователя)
  - `usedSpaceBytes` (агрегированное занятое место для ускорения проверок)
  - `createdAt`, `updatedAt`

- **Folder**
  - `id` (UUID, PK)
  - `userId` (FK → User)
  - `name`
  - `parentFolderId` (nullable, FK → Folder) — для вложенной иерархии
  - `createdAt`, `updatedAt`
  - Логика построения пути:
    - Поле `path` (например, `/docs/personal`), вычисляемое и/или хранимое для ускорения поиска

- **FileEntry**
  - `id` (UUID, PK)
  - `userId` (FK → User)
  - `folderId` (nullable, FK → Folder) — корневые файлы, если `null`
  - `originalName` (имя файла, видимое пользователю)
  - `storageFilename` (имя файла на диске, уникальное, например UUID)
  - `sizeBytes`
  - `mimeType`
  - `hash` (опционально, для идентификации дубликатов/проверок целостности)
  - `createdAt`, `updatedAt`
  - Флаг `isPreviewGenerated` и ссылка на превью (опционально, для видео/изображений в будущем)

- **ShareLink**
  - `id` (UUID, PK)
  - `token` (короткий публичный идентификатор в URL)
  - `ownerUserId` (кто создал ссылку)
  - `fileId` (FK → FileEntry, nullable)
  - `folderId` (FK → Folder, nullable)
  - Ограничение: либо `fileId`, либо `folderId` заполнено (но не оба)
  - `expiresAt` (дата истечения срока)
  - `createdAt`

- **(На будущее) AuditEntry**
  - `id`
  - `userId`
  - `action` (UPLOAD_FILE, DELETE_FILE, CREATE_FOLDER, etc.)
  - `targetFileId`/`targetFolderId`
  - `timestamp`

#### 2.2. Связи и инварианты

- Один `User` → много `Folder`, `FileEntry`, `ShareLink`.
- Общий объём файлов пользователя = сумма `FileEntry.sizeBytes` по `userId`.
- `User.usedSpaceBytes` должен быть консистентен с суммой файлов (пересчёт периодическим job-ом либо строго поддерживать в транзакциях при изменениях).
- Нельзя сохранять файл, если `usedSpaceBytes + size > assignedSpaceBytes`.
- При удалении файла:
  - удаляем запись `FileEntry`
  - физически удаляем файл с диска
  - уменьшаем `usedSpaceBytes`
  - инвалидируем связанные `ShareLink`.

### 3. Хранение файлов (файловая система)

- Базовый каталог для файлов:
  - конфигурация: `storage.root-path`, по умолчанию `backend/cloud`
  - можно переопределить через переменные окружения.
- Структура:
  - `storage.root-path/{userUuid}/{nested_path_from_folders}/{storageFilename}`
  - `nested_path_from_folders` строится из иерархии `Folder` (например, `/docs/personal/`).
- Класс-абстракция:
  - Интерфейс `FileStorage` с методами:
    - `store(user, folder, inputStream, size, mimeType) -> FileEntry`
    - `load(FileEntry) -> InputStreamResource/Resource`
    - `delete(FileEntry)`
  - Имплементация `LocalFileStorage` (работа с локальным диском).
- Требования:
  - Использовать стриминг (не загружать весь файл в память).
  - Обрабатывать большие файлы (ограничение задаётся конфигом, проверка до приёма).

### 4. Безопасность и аутентификация (Spring Security + JWT)

- **Регистрация (self-signup):**
  - Endpoint `POST /api/auth/signup`
    - вход: `username`, `password`
    - действие: создаём пользователя с дефолтным лимитом `assignedSpaceBytes`, `usedSpaceBytes = 0`, роль `USER`.
  - Проверка уникальности `username`.

- **Логин:**
  - Endpoint `POST /api/auth/login`
    - вход: `username`, `password`
    - при успехе: возвращаем JWT-токен и базовую инфу о пользователе (id, username, лимит, used).

- **JWT:**
  - Хранение секретного ключа в конфигурации/переменных окружения.
  - Фильтр, который:
    - читает Authorization: Bearer `<token>`
    - валидирует
    - создаёт `Authentication` в SecurityContext.

- **Роли:**
  - `USER`: доступ к своим файлам/папкам.
  - Для админки backend предоставляет `/api/admin/...`, защищённые ролью `ADMIN` (пока можно создать администратора руками или через отдельный endpoint).

- **Публичный доступ:**
  - `GET /api/share/{token}` — доступ без авторизации (если ссылка активна и не просрочена).

### 5. API (основные модули)

#### 5.1. Auth API

- `POST /api/auth/signup`
- `POST /api/auth/login`
- Опционально: `GET /api/auth/me` — данные текущего пользователя (по токену).

#### 5.2. File & Folder API (для пользователя)

- **Папки:**
  - `POST /api/folders` — создать папку
  - `GET /api/folders` — список корневых папок и/или дерева
  - `GET /api/folders/{id}` — содержимое папки: список файлов и подпапок
  - `DELETE /api/folders/{id}` — удалить папку (включая вложенные файлы/папки)

- **Файлы:**
  - `POST /api/files/upload`
    - multipart: `file`, `folderId?`
    - проверка квоты (до записи файла и после)
  - `GET /api/files/{id}/download`
    - отдача файла (с корректными заголовками для скачивания)
  - `GET /api/files/{id}/preview`
    - отдача файла/превью для отображения в браузере (для изображений/текста/видео)
  - `GET /api/files/{id}/meta`
    - метаданные файла (имя, размер, mime, путь и т.п.)
  - `DELETE /api/files/{id}`
    - жёсткое удаление + обновление `usedSpaceBytes`.

#### 5.3. Share API (механизм "поделиться")

- `POST /api/share`
  - вход: `fileId` или `folderId`, `ttl` (один из предопределённых: 1h, 24h, 7d, 30d)
  - создаёт `ShareLink`, возвращает публичный URL `/share/{token}`.

- `GET /api/share/{token}`
  - если ссылка валидна и не истекла:
    - если это файл: либо скачивание, либо предпросмотр (в зависимости от параметров/фронта)
    - если это папка: список содержимого (для начала можно скачать архив папки позже).

- `DELETE /api/share/{id}` (или по token)
  - отозвать ссылку.

#### 5.4. Quota API

- Внутренняя логика в `QuotaService`:
  - метод `checkCanStore(userId, fileSize)`, бросающий исключение при превышении.
  - метод `recalculateUserQuota(userId)` — на будущее, для пересчёта.

### 6. Админские API (для admin frontend)

- Префикс: `/api/admin/...` (роль `ADMIN`).

- **Статистика/дашборд:**
  - `GET /api/admin/stats/summary`
    - общее занятое место
    - количество пользователей
    - количество файлов
  - `GET /api/admin/stats/users`
    - список пользователей с полями: `username`, `assignedSpaceBytes`, `usedSpaceBytes`.

- **Управление пользователями:**
  - `GET /api/admin/users`
  - `PATCH /api/admin/users/{id}/quota`
    - изменить `assignedSpaceBytes`.

- **(Опционально) Аудит:**
  - `GET /api/admin/audit` — фильтры по пользователю/типу операции.

---

### 7. Multithreading и асинхронные задачи

- Использовать Spring `@EnableAsync` + `TaskExecutor`:
  - Конфигурация пула потоков (corePoolSize, maxPoolSize, queueCapacity).
- Примеры асинхронных задач:
  - Генерация превью/thumbnail для изображений и видео (вынести в отдельный `PreviewService`):
    - после успешной загрузки файла запускаем асинхронную задачу.
  - Периодический job (через `@Scheduled`):
    - очистка просроченных `ShareLink`.
- Важно:
  - Чётко отделять синхронный путь (загрузка/скачивание) от фоновых задач.
  - Не блокировать HTTP-потоки тяжёлыми операциями (конвертация, генерация превью).

---

### 8. Документация API (OpenAPI/Swagger)

- Подключить Springdoc OpenAPI:
  - зависимость `springdoc-openapi-starter-webmvc-ui`.
  - Автогенерация спецификации.
- Доступ:
  - UI: `/swagger-ui.html` или `/swagger-ui/index.html`.
  - JSON-спецификация: `/v3/api-docs`.
- Обновлять описания через аннотации (`@Operation`, `@Schema`).

### 9. Конфигурация и окружение

- Основные параметры в `application.yml`:
  - `spring.datasource.*` для SQLite.
  - `storage.root-path`.
  - `jwt.secret`, `jwt.expiration`.
  - Настройки пула потоков для async-задач.
  - Максимальный размер загружаемого файла.
- Параметры должны быть переопределяемы через env-переменные (для Docker).

---

### 10. Docker и docker-compose

- Dockerfile для backend:
  - сборка JAR через Maven
  - запуск JAR в контейнере.
- `docker-compose.yml` в корне:
  - сервис `backend`:
    - монтирование volume для:
      - файла SQLite (`/data/db.sqlite`)
      - директории файлов (`/data/cloud`)
    - проброс порта (например, `8080:8080`).
- При локальной разработке:
  - возможность запускать backend без Docker (просто `mvn spring-boot:run`), при этом использовать те же пути, но локально.

### 12. Брейкпоинты для старта фронтенда и админки

- **Брейкпоинт F1 — старт пользовательского фронтенда (auth + базовый UI):**
  - Backend: завершены шаги `1–3` (инфраструктура, модели, базовый auth API `signup/login`).
  - Можно:
    - реализовать формы регистрации/логина;
    - настроить хранение/обновление JWT на фронте;
    - сделать базовый layout и маршруты (личный кабинет, список файлов — пока заглушки).

- **Брейкпоинт F2 — фронтенд работа с файлами и папками:**
  - Backend: дополнительно завершены шаги `4–5` (FileStorage, `FileService`, `FileController`, `FolderController`, квоты).
  - Можно:
    - реализовать UI для создания папок;
    - реализовать загрузку файлов (drag&drop / input), отображение прогресса;
    - показать дерево/список папок и файлов, предпросмотр/скачивание;
    - обрабатывать ошибки квот (отображать сообщения от backend).

- **Брейкпоинт F3 — фронтенд для шаринга:**
  - Backend: реализован шаг `6` (Share API).
  - Можно:
    - добавить в UI создание публичных ссылок (для файла/папки);
    - отображать срок действия ссылки и давать возможность её отозвать;
    - реализовать отдельную страницу открытия по публичному токену (без авторизации).

- **Брейкпоинт A1 — старт админки (просмотр статистики):**
  - Backend: завершены шаги `1–3` + есть базовые сущности `User`, `FileEntry`.
  - Можно начать:
    - интегрировать админскую авторизацию (отдельный логин в admin frontend, работающий с backend через `ADMIN`-endpoint’ы);
    - подготовить UI-скелет админ-панели (дашборд, список пользователей) — пока можно использовать моковые данные.

- **Брейкпоинт A2 — полноценный дэшборд и управление пользователями:**
  - Backend: завершены шаги `6–7` (Share API, Admin API: статистика и изменение квот).
  - Можно:
    - реализовать дэшборд (общая статистика + статистика по пользователям);
    - добавить UI для изменения квоты пользователей;
    - при необходимости отрисовывать шаринги/активность (после добавления аудита).

- **Брейкпоинт F/A-final — полная интеграция:**
  - Backend: шаги `8–10` (multithreading, превью, планировщик, Swagger, обработка ошибок, финальные проверки).
  - Можно:
    - интегрировать превью в пользовательский фронтенд (миниатюры, предпросмотр видео/изображений);
    - использовать документацию Swagger для тонкой настройки запросов на фронтах;
    - доводить UX и визуал на обеих частях (frontend + admin).
