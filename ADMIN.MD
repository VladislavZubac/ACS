## Технический план admin frontend для "Мини-облако"

### 1. Общая архитектура и стек

- **Стек:**
  - Отдельное приложение Next.js 16 (App Router)
  - React 19, TypeScript
  - Tailwind CSS (тот же визуальный стиль, что и user-frontend)
  - TanStack Query для работы с admin API
- **Принципы:**
  - Модульность: доменные модули `admin/auth`, `admin/dashboard`, `admin/users`, общие UI-компоненты.
  - Минимум хардкода: конфигурация через env (`NEXT_PUBLIC_ADMIN_API_BASE_URL` и др.).
  - Стиль как у user-frontend (современный, без излишеств), но более табличный и “информационный”.
  - Админская авторизация полностью отдельная от пользовательской (свои эндпоинты и учётки).

---

### 2. Основные страницы и маршруты

- **Маршруты:**
  - `/admin/login` — страница входа администратора.
  - `/admin` или `/admin/dashboard` — главный дэшборд со статистикой.
  - `/admin/users` — список пользователей.
  - `/admin/users/[id]` — страница конкретного пользователя (подробности + изменение квоты).

- **Маршрутизация и защита:**
  - Неавторизованный админ при заходе на `/admin/...` → редирект на `/admin/login`.
  - Авторизованный админ при заходе на `/admin/login` → редирект на `/admin/dashboard`.

- **Layouts:**
  - `app/(auth)/admin/login` — простой layout без сайдбара.
  - `app/(admin)/admin/...` — layout с верхней панелью и сайдбаром:
    - верх: название, переключатель темы, кнопка logout;
    - слева: ссылки `Dashboard`, `Users`.

---

### 3. Админская аутентификация и состояние

- **Auth слой:**
  - Отдельный `AdminAuthContext` / `useAdminAuth`:
    - хранит токен админа и базовую информацию (username администратора).
    - методы: `login`, `logout`.
  - JWT админа хранится в `localStorage` (отдельный ключ, например `admin_token`).
  - При загрузке admin-приложения:
    - читаем токен из storage, при наличии валидируем/запрашиваем `/api/admin/auth/me` (если такой endpoint будет).

- **Admin API-клиент:**
  - Свой `adminApiClient` с базовым URL из `NEXT_PUBLIC_ADMIN_API_BASE_URL`.
  - Перехватчик добавляет `Authorization: Bearer <admin_token>`.
  - 401 → logout и редирект на `/admin/login`.

---

### 4. Дэшборд администратора

- **Страница `/admin/dashboard`:**
  - Запрос к `/api/admin/stats/summary`.
  - Отображаем:
    - общая занятость диска (ГБ + процент);
    - количество пользователей;
    - количество файлов.
  - UI:
    - 2–3 card-компонента с ключевыми цифрами;
    - простая полоска прогресса для общей занятости.
  - Графики роста/динамики на данном этапе **не нужны**.

---

### 5. Управление пользователями

- **Страница `/admin/users`:**
  - Таблица пользователей:
    - колонки: `username`, `assignedSpaceBytes`, `usedSpaceBytes`, процент использования.
  - Действия:
    - клик по строке → переход на `/admin/users/[id]`.
  - Поиск/фильтры по пользователям на первом этапе **не требуются**.

- **Страница `/admin/users/[id]`:**
  - Информация о пользователе:
    - `username`;
    - `assignedSpaceBytes`;
    - `usedSpaceBytes`.
  - Возможности:
    - изменение квоты (`assignedSpaceBytes`) через форму (input/slider) + сохранение:
      - `PATCH /api/admin/users/{id}/quota`.
  - Другие действия (блокировка, удаление, управление файлами, share-ссылками) в первой версии **отсутствуют** — по брейкпоинтам backend, можно добавить позже.

---

### 6. Просмотр логов

- **Источник логов:**
  - Логи приходят с backend (способ получения определяется позже: простой endpoint, который отдаёт последние N строк, либо файл/стрим).

- **Страница `/admin/logs` (опциональная, можно добавить после A1):**
  - Простой текстовый viewer:
    - area/блок с монопробельным шрифтом, прокруткой;
    - кнопка “Обновить” для рефреша.
  - Отображаются последние N строк логов (например, `GET /api/admin/logs?tail=500`).
  - Фильтрация/поиск по логам на первом этапе не обязательны.

---

### 7. Темы, стиль и UX

- Стиль как у пользовательского frontend:
  - Tailwind, поддержка light/dark.
  - Переключатель темы в верхнем баре.
- Язык интерфейса: русский.
- Основной упор — на читаемость таблиц и цифр, минимум лишней графики.

---

### 8. Обработка ошибок и состояний

- Ошибки API:
  - модалки/диалоговые окна с сообщениями (“Ошибка сервера”, “Нет доступа”, “Не удалось обновить квоту”).
  - 401 → logout и редирект на `/admin/login`.
- Loading:
  - skeleton/спиннер на дэшборде;
  - состояние загрузки таблицы пользователей и страницы пользователя.
- Состояния “backend недоступен”:
  - понятное сообщение на дэшборде (“Backend недоступен, проверьте сервер”) + кнопка “Повторить”.

---

### 9. Модульность admin frontend

- Структура модулей:
  - `admin/auth` — страницы логина, контекст авторизации.
  - `admin/dashboard` — дэшборд, компоненты карточек и прогресс-бара.
  - `admin/users` — список пользователей и страница пользователя.
  - `admin/logs` — viewer логов (по мере реализации backend-части).
  - `admin/shared/ui` — общие UI-компоненты (layout, таблицы, модалки, карточки).
- Те же принципы, что и в user frontend:
  - доменное разделение, переиспользуемые компоненты, минимум хардкода, конфигурация через переменные окружения.

---

### 10. Брейкпоинты A1/A2 и связь с backend

- **A1 — старт admin-панели:**
  - Требования от backend:
    - реализованы базовые admin-endpoint’ы аутентификации;
    - `AdminStatsController` (summary),
    - базовые данные о пользователях (список, квоты, used space).
  - На admin frontend реализуем:
    - `/admin/login`,
    - `/admin/dashboard` (без логов),
    - `/admin/users` и `/admin/users/[id]` с возможностью изменять квоту.

- **A2 — расширение admin-панели:**
  - Требования от backend:
    - дополнительные admin API (например, логи, более детальная статистика, аудит — по мере появления).
  - На admin frontend можно добавить:
    - `/admin/logs` с просмотром последних логов,
    - дополнительные карточки/метрики на дэшборде,
    - (в будущем) разделы для аудита и более тонкого управления.
